Windows MSI — rules that keep installs updatable:
- `HKCU\Software\Prism` (`InstallType`, `InstallDir`, `InstalledVersion`) is the contract between the package and the app. `platform.MSIInstallDir()` reads it and `desktop.InstalledViaMSI()` matches it against the running exe; renaming any of those values silently turns MSI installs back into "portable".
- Never let the portable update flow (`performPortableUpdate` in `internal/desktop/update_windows.go`) write over an MSI-managed `prism.exe`: Windows Installer owns that file and reverts it on the next repair or upgrade. MSI installs download the `.msi` asset and hand it to `msiexec` (`performMSIUpdate`), which is also why `updateAssetShapes()` (the version-tolerant replacement for the old exact-name `getUpdateAssetName`/`updateAssetCandidates`) is per-OS.
- The MSI takes over `HKCU\...\Run\Prism` only when `PRISM_AUTOSTART_PATH` (a `RegistrySearch`) finds an entry already there: the `AutoStartValue` component is conditioned on that property, so a stale value — typically one left by a dev checkout or a portable copy — is repointed at the installed exe and MSI owns the row for uninstall, while a fresh install never switches auto-start on behind the user's back. An unconditional `RemoveRegistryValue` would be wrong: it also fires while a major upgrade uninstalls the previous product, silently disabling "Start at Login" on every update. `platform.SyncAutoStartPath()` (called from `desktop.RunTray`) covers the portable and moved-exe cases.
- `Scope="perUser"` is the whole install-context mechanism, and the **registration location does not indicate elevation**. The per-user flag (summary info Character Count bit 3) makes Windows Installer install per-user without elevation; it also **deletes an authored `ALLUSERS` and ignores `MSIINSTALLPERUSER`** ("MSIINSTALLPERUSER property is not valid for UAC compliant package. Ignoring"), so authoring the documented `ALLUSERS=2` + `MSIINSTALLPERUSER=1` pair is a no-op — measured, not assumed. A per-user package registers under `HKLM\...\Installer\UserData\<SID>\Products` with its ARP entry in `HKLM\...\Uninstall` even when nothing was elevated, so **do not** "fix" that by adding properties: a silent non-elevated install, upgrade and uninstall of this package shape all return 0, which is why `performMSIUpdate` needs no elevation. `build-msi.ps1` asserts this (`Assert-MsiScope`: flag set for `perUser`, `ALLUSERS=1` and the flag clear for `perMachine`) plus the auto-start takeover (`Assert-MsiAutostartAdoption`).
- A per-machine MSI needs an elevated `msiexec`; the updater does not elevate, so `-Scope perMachine` packages are manual-install only until `performMSIUpdate` learns to elevate.
- **Windows Installer compares PE file versions, not Prism's semantic app version.** Early CI builds inherited go-winres' default `1.0.0.0`, while release builds used versions such as `0.3.23`; during a major upgrade MSI judged the release exe older, planned no copy, then removed the old product's copy. A FileRef launch action then failed with 2753 and rolled back the upgrade. The Windows workflow now stamps all builds with a monotonically increasing PE version derived from this workflow's increasing `GITHUB_RUN_NUMBER` (while ProductVersion remains semantic); `build-msi.ps1` rejects payloads that don't have the expected `2.<run high bits>.<run low bits>.0` version. For a manual MSI build, run `go-winres make --file-version 2.0.<unique-run>.0 --product-version <semantic-version>` before `go build`; the PE version must be higher than any previously installed MSI payload.
- **Author `Feature`, `CustomAction`, and `util:` actions inside `<Package>`, not in their own `<Fragment>`.** WiX v6 silently discards anything that is not reachable from `<Package>`: the build exits 0, prints no warning, and emits an MSI with no `File` rows, no `Component` table and no payload. This shipped once as a 28 KB `Prism-Windows-x64.msi` (see the comment in `Prism.wxs`). `build-msi.ps1` now reads the built database back with `Assert-MsiFilePayload` (payload), `Assert-MsiScope` (install context), `Assert-MsiAutostartAdoption` (auto-start takeover), `Assert-MsiLaunch` (launch action), and `Assert-MsiShortcutTarget` (the Start Menu shortcut still points at `[INSTALLFOLDER]prism.exe`) and fails if any of them is wrong, so a green build can no longer mean a broken package.

Release asset names — version-stamped, with unversioned aliases:
- Every artifact is published twice: under its version-stamped name (`prism-0.9.1.exe`, `Prism-0.9.1-Windows-x64.msi`, `Prism-0.9.1-macOS.dmg`, `Prism-0.9.1-macOS.tar.gz`, `Prism-0.9.1-Linux.tar.gz`, `Prism-0.9.1-Linux-x86_64.AppImage`) and under the unversioned name releases used before version stamping. Each job's "Prepare release asset names" step copies the first to the second and fails if any of the four is missing, so a forgotten alias is a red build rather than a silent one-way door.
- The aliases exist because an install shipped before version stamping looks its download up by **exact asset name**. Dropping one without the updater's fallback silently stops auto-update for every copy in the field, and the updater on those installs cannot be fixed after the fact. Retire them only once no install old enough to need them is still updating (not before a couple of releases that carry both names), and retire them in the same change as the upload lists.
- `internal/desktop/update_assets.go` is the version-tolerant replacement: it matches a release asset by *shape* (`{Product, Tail}`, e.g. `{"Prism", "-Windows-x64.msi"}`), so one shape covers the version-stamped name and the alias. Within a shape the version-stamped name for the release's own tag wins — never a stale alias — and the unversioned name is the fallback. `update_assets_test.go` pins every published name, so renaming an asset in the workflow without updating the shape (or vice versa) fails the test suite.
- Non-tag (pull-request) builds cannot put `$GITHUB_REF_NAME` in a file name (`123/merge` is not a usable name), so all three jobs derive the same filesystem-safe token: the numeric tag on a tag push, otherwise `0.0.<run % 60000>` — the same value the PR MSI has always used as its version. `-X main.version` still gets the raw ref, so the displayed version is unchanged.
- The Windows job builds `prism-<version>.exe`. `Prism.wxs` pins `File/@Name="prism.exe"` so the **installed** file keeps that name regardless of what the build output is called: `util:CloseApplication` matches the running image by name, the `HKCU\...\Run\Prism` value and the Start Menu shortcut point at `[INSTALLFOLDER]prism.exe`, and `InstalledViaMSI` compares directories. `build-msi.ps1` asserts the installed name (`Assert-MsiFilePayload -FileName prism.exe`), never `Split-Path $exeFull -Leaf` — deriving it from the artifact would quietly stop checking the payload once CI version-stamps the build.
- The macOS job stamps `CFBundleShortVersionString` and `CFBundleVersion` into the *bundled* `Info.plist` (the tracked file stays a placeholder) **before** codesign, since the signature covers the plist. The Linux job appends `X-AppImage-Version` to the AppDir copy of `prism.desktop` before `appimagetool`; the tracked `packaging/linux/prism.desktop` stays version-free. In both cases only the packaged copy carries the version.
- The tarballs still contain a plain `Prism.app` / `prism` binary; the updater unpacks them over the installed path, so only the archive name is versioned.
- The portable `prism-<version>.exe` and the AppImage replace themselves in place on an in-app update, so their file name describes what was downloaded, not what is currently running. That is expected, not a bug to "fix" by renaming on update.
- Frontend build output is already content-hashed by Vite (`web/dist/assets/index-<hash>.js`). `adminStaticCacheControl` in `internal/admin/admin.go` serves `assets/` as `immutable` and everything else under `web/dist` (files copied from `web/public/` have stable names) plus the `index.html` responses as `no-cache`, so a rebuilt bundle is picked up without a hard refresh.

Committing, pushing, and releasing — explicit permission required:
Do NOT commit, push, or create any release tag unless the user explicitly asks for it in the
current request (e.g. "commit this", "push", "cut a release"). Making file edits, staging, and
showing diffs is fine; writing to git history or the remote is not. When in doubt, stop and ask.
This applies even after a task is finished — finishing the work is not permission to commit it.

Committing and pushing:
1. Stage and commit changes: `git add -A; git commit -m "message"`
2. Push to remote: `git push origin main`
3. Always verify no secrets/credentials are in the diff before committing (`git diff --cached`)

Creating a release:
1. Create an annotated tag: `git tag -a v0.X.Y -m "Release title\n\nRelease notes here"`
2. Push the tag: `git push origin v0.X.Y`
3. The GitHub Actions workflow (`.github/workflows/release.yml`) will automatically build and create a GitHub Release with every artifact under both its version-stamped and its unversioned name: `prism-0.9.1.exe`/`prism.exe`, `Prism-0.9.1-Windows-x64.msi`/`Prism-Windows-x64.msi`, `Prism-0.9.1-macOS.dmg`/`Prism-macOS.dmg`, `Prism-0.9.1-macOS.tar.gz`/`Prism-macOS.tar.gz`, `Prism-0.9.1-Linux.tar.gz`/`Prism-Linux.tar.gz` and `Prism-0.9.1-Linux-x86_64.AppImage`/`Prism-Linux-x86_64.AppImage`
4. The tag version is injected into the binary via `-X main.version=$GITHUB_REF_NAME`. Tags must be `v<major>.<minor>.<build>`: the MSI, the PE version resource and the version-stamped asset names all need numeric versions, and every job fails early on anything else (a pull request builds the same artifacts under `0.0.<run % 60000>`).
5. Release assets must match what the auto-updater expects, under both names — the version-stamped one for releases cut from now on, the unversioned one for installs that predate version stamping (the job fails if either is missing): `prism-<version>.exe` and `prism.exe`, `Prism-<version>-Windows-x64.msi` and `Prism-Windows-x64.msi` (Windows); `Prism-<version>-macOS.tar.gz` and `Prism-macOS.tar.gz` (macOS); `Prism-<version>-Linux.tar.gz`/`Prism-Linux.tar.gz` plus the matching AppImage pair (Linux)
